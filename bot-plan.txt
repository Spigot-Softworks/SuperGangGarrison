## Current implementation status and validation gate

The current alpha implementation is a prototype, not an accepted navigation system.
It can build a compact OG2-derived graph and report abstract graph paths, but an
abstract `spawn -> objective` path is not evidence that a bot can physically
execute the route. The first alpha runtime trial did not complete the outbound
Truefort trip to the enemy intel, so the graph must currently be treated as
untrusted.

This distinction is now an explicit development gate:

```text
Graph reports a path
    -> trace the exact edge sequence
    -> validate each edge against the OG2 movement model
    -> execute the same edge sequence in the runtime
    -> classify the failure as graph or executor
```

Debugging order is mandatory:

1. Establish a deterministic Truefort spawn-to-enemy-intel route. The outbound
   route is the descent over the stair platforms; the carrier return is a
   separate ascent route and must not be used as the first outbound diagnosis.
2. For every generated edge on that route, record its source/target coordinates,
   link kind, completion recipe, support/clearance assumptions, and runtime
   result.
3. If the OG2 movement validator rejects an edge, the graph generator is wrong
   or overly permissive. Fix the graph before tuning steering.
4. If the movement validator accepts an edge but runtime execution fails, fix
   the route executor or steering contract without weakening graph validity.
5. Only after the outbound capture is physically proven should carrier return,
   other objectives, other classes, and the stock-map matrix be expanded.

The current hard acceptance gate is therefore:

- no graph-level reachability result counts as a pass by itself;
- no generated edge may rely on an unverified broad heuristic that the runtime
  cannot execute;
- Truefort outbound capture must pass before return-path work is considered
  complete;
- the full class/map matrix remains blocked until both directions pass on the
  focused Truefort test.

Known current status: Core and the diagnostic tool compile, the alpha graph and
diagnostic harness exist, but Truefort outbound runtime capture is not yet
passing and the requested stock-map/class matrix has not been accepted.

## Immediate pivot: authoritative contact graph

The heuristic alpha graph is not a valid navigation graph and is no longer a
candidate for incremental tuning. In particular, the previous stair/step
profile admitted long links that looked plausible in geometry but could not be
executed by OG2. The graph must not be made to appear reachable by adding broad
relays, objective-specific exceptions, or carrier-only capabilities.

The next implementation milestone is an authoritative local-contact graph:

1. Extract a shared geometry snapshot and topology-change surface intervals.
2. Place only local contact/portal samples at surface boundaries, step changes,
   corridor mouths, objective approaches, and spawn approaches.
3. Run bounded OG2 movement sweeps from those samples in both directions. A
   contact is emitted only when the real `PlayerEntity` movement model reaches
   and settles on the recorded destination surface.
4. Store the resulting directional contacts as geometry capabilities. They are
   never gated by carrying intel, objective role, or carrier state. A non-carrier
   must be able to use the same ascent/descent contact when its class can move
   through it.
5. Collapse equivalent contacts across representative movement profiles into
   one shared topology with conservative physical capability metadata.
6. Convert the validated contact sequence into the runtime graph and execute
   that exact sequence in the bot harness.

The first hard proof is Truefort spawn -> enemy intel. This is the outbound
descent over the stair platforms. The return ascent is a separate proof after
the outbound route passes; it is not carrier-only and must also be usable by a
bot chasing, defending, or otherwise entering the corridor without intel.

Until this contact graph proves that route edge-by-edge, the existing alpha
graph remains diagnostic-only, steering/objective behavior remains frozen, and
no stock-map/class matrix result may be reported as a navigation pass.

## Diagnosis of the existing navigation stack

The current system is not one navigation system. It is several competing systems:

```mermaid
flowchart TD
    O[ObjectiveEvaluator] --> B[BotBrainController]
    B --> G[Cached NavGraph]
    B --> S[SteeringMachine]
    B --> D[Direct Seek]
    B --> L[Local Motion]
    B --> P[Primitive Direct Drive]
    B --> T[Objective Tapes]
    B --> V[Verified Proof Routes]
    B --> C[Map-Specific Repairs]
```

Important findings:

1. The live controller calls `TryLoadCachedGraph`; it does not normally call the available `LoadGraphOrBuild` path. Missing or invalid graphs therefore enter `ThinkWithoutNavigationGraph`, where direct seek and local motion take over.

2. The current asset builder is already a large, sophisticated system, but it is doing too much:
   - surface extraction
   - portal generation
   - pairwise candidate discovery
   - runtime movement simulation
   - class/team certification
   - map-specific repairs
   - authored corridors
   - proof-route integration
   - objective anchoring

3. Existing shipped assets demonstrate the cost problem:

   - roughly 129–1,000 nodes per map
   - roughly 378–9,548 edges
   - up to 42,872 node-pair checks
   - up to 21,128 movement-probe attempts
   - assets ranging from hundreds of KB to over 7 MB

   Some maps still report spawn/objective reachability failures despite this effort, notably Destroy, Dirtbowl, Egypt, and Gallery.

4. `NavGraph` performs brute-force nearest-node searches and allocates fresh arrays and priority queues for reachable-node and path queries.

5. `BotBrainMovementProbe` simulates `PlayerEntity` instances for many candidate edges, across multiple profiles, teams, launch timings, and variants. This is fundamentally too expensive for a runtime-first generator.

6. The graph is not fully class/team agnostic today. Its topology is shared, but edge metadata contains class/team masks produced by probing selected classes—primarily Heavy, Soldier, and Scout—and runtime filtering depends on those masks.

7. Movement ownership is fragmented. `SteeringMachine`, objective tapes, proof routes, direct seek, local-motion recovery, primitive drive, and map-specific methods can all override one another.

8. `ObjectiveEvaluator` is comparatively clean and should remain. Combat, targeting, medic behavior, class behavior, and objective selection should not be rewritten as part of navigation.

The existing tests confirm this architecture. For example, [BotBrainNoGraphFallbackTests.cs](<C:/Users/level/Desktop/OpenGarrison Active/OpenGarrison-Fork/Tests/OpenGarrison.PluginHost.Tests/BotBrainNoGraphFallbackTests.cs:8>) intentionally validates direct-seek behavior when navigation is missing, while [BotBrainNavigationCostTests.cs](<C:/Users/level/Desktop/OpenGarrison Active/OpenGarrison-Fork/Tests/OpenGarrison.PluginHost.Tests/BotBrainNavigationCostTests.cs:9>) encodes several map-specific routing penalties.

## Recommended architecture: an OG2-native surface/portal graph

The replacement should not be a rebuilt version of the old graph. It should be a smaller, runtime-generated graph derived directly from the current OG2 simulation model.

The key design is:

- static geometry topology
- dynamic traversal policies
- objective goal regions
- compact transition links
- deterministic route execution

```mermaid
flowchart TD
    L[SimpleLevel + OG2 collision/object metadata] --> S[Geometry Snapshot]
    S --> X[Walkable Surface Extraction]
    X --> P[Portal and Anchor Extraction]
    P --> E[Analytic Link Generation]
    E --> A[Objective Goal Regions]
    A --> G[Immutable Og2NavGraph]

    G --> Q[Nav Query Context]
    Q --> R[A* Route]
    R --> F[Route Executor]
    F --> I[PlayerInputSnapshot]

    D[Dynamic gates/objective state] --> Q
    C[Class movement profile] --> Q
    T[Team/carrying-intel policy] --> Q
```

### 1. Immutable geometry snapshot

Create a compact `Og2NavigationGeometry` snapshot from `SimpleLevel`.

It should contain:

- world bounds and level fingerprint
- static solid rectangles
- walk-blocking room objects
- dropdown platforms
- team gates and intel gates
- directional walls and barriers
- teleports, catapults, jump pads, and moving-platform metadata
- spawn regions
- intel base regions
- control-point and capture-zone regions
- generator and arena-objective regions

The snapshot must be independent of `PlayerEntity` instances and safe to build once per level.

### 2. Surface regions instead of dense waypoint chains

A surface should be a horizontal walkable interval:

```text
Surface:
    leftX
    rightX
    topY
    clearance
    flags
```

Generate surfaces by taking exposed solid top edges and subtracting intervals blocked by other geometry. Merge adjacent coplanar intervals.

Do not create a waypoint every 80 pixels. A long flat floor should be one surface region with implicit movement along its X interval.

This removes most unnecessary nodes and makes movement naturally smooth.

### 3. Portals and anchors

Create portals only where topology changes:

- surface endpoints
- step transitions
- jump launch/landing bands
- drop/fall edges
- dropdown transitions
- special-object entry/exit points
- narrow corridor entrances
- objective approach points

Objectives should not be represented as one raw center node. They should be represented as goal regions with multiple valid standing slots.

For a control point, the goal region should derive from the actual capture zone, because capture logic uses the zone geometry rather than merely the control-point marker center. A goal region can contain:

- center slot
- left/right slots
- upper/lower slots where geometry permits
- approach slots just outside the capture area

The resolver chooses the closest reachable slot, not the mathematically nearest point.

### 4. Class/team-agnostic links

The graph topology must never be duplicated per class or team.

A link stores physical requirements, not class IDs:

```text
Link:
    fromPortal
    toPortal
    kind
    baseCost
    horizontalDistance
    verticalDelta
    requiredClearance
    requiredJumpHeight
    requiredFallCapacity
    executionRecipe
    dynamicPolicyReference
```

At query time, a `NavTraversalContext` supplies:

- player class movement profile
- team
- carrying-intel state
- current dynamic gate state
- objective mode/state

This preserves one graph while allowing the runtime to reject links a specific agent cannot use.

Team gates, barriers, and intel gates should be policy checks, not separate graphs.

### 5. Contact-first link generation

Analytic geometry is a candidate prefilter only. It may bound the local sweep
neighborhood and reject impossible clearance/range pairs, but it cannot certify
that a link is traversable. Every emitted step, jump, fall, and dropdown link
must come from a bounded OG2 movement sweep that records the actual contact and
settled destination.

The build pipeline is:

1. snapshot level geometry
2. extract exposed walkable intervals
3. merge/prune surfaces
4. create topology-change contacts and objective/spawn approach samples
5. query only spatially adjacent contact candidates
6. run short directional OG2 sweeps from each candidate in both directions
7. emit only contacts with a settled destination and an executable recipe
8. validate connected components and objective reachability
9. publish one immutable graph

This deliberately spends bounded simulation time on local contacts instead of
spending unbounded time on pairwise heuristic edges. Runtime probing is not a
fallback after generation; it is the authority for ambiguous traversal.

## Runtime query and movement model

The new runtime should provide:

```text
Og2NavWorld
    Immutable graph
    Spatial attachment index
    Dynamic policy/version state
    Reusable pathfinding scratch buffers

NavQueryContext
    Class profile
    Team
    Carrying intel
    Current objective state

NavRoute
    Surface corridors
    Transition links
    Goal region/slot

NavRouteExecutor
    Walk corridor
    Jump recipe
    Drop recipe
    Special transition recipe
```

Key runtime behavior:

- attach the bot to the nearest valid surface interval using a spatial index
- attach the objective to a reachable goal slot
- run A* over portals/surface regions
- move along a surface corridor implicitly
- execute transitions using explicit link recipes
- replan only on route invalidation, failed transition, major goal change, or periodic health interval
- use reusable arrays/queues so steady-state navigation allocates nothing

`FindNearestReachableNode` should disappear. The route query should directly search for the best reachable goal slot using the current context.

## Dynamic state handling

The static graph should not be rebuilt when:

- a control point changes ownership
- a player carries intel
- a setup gate expires
- a team gate changes accessibility
- a forward-spawn state changes

Instead, these become dynamic policy checks attached to links.

The existing semantics in `SimpleLevel.GetBlockingTeamGates`, `PlayerEntity.CanOccupy`, control-point capture logic, and intel logic should be centralized behind a navigation-access policy so the graph and simulation agree.

Dynamic state should have a small version counter. Routes cache the version they were planned against and invalidate when relevant policy changes.

## Objective integration without changing behavior

Keep `ObjectiveEvaluator`, target selection, combat decisions, medic logic, spy behavior, and class behavior unchanged.

Only replace the travel seam:

```text
Existing behavior logic
    -> existing objective/target decision
    -> navigation goal resolver
    -> new graph route
    -> new route executor
```

The first integration can continue accepting the evaluator’s `(X, Y)` output, with a resolver that recognizes nearby control points, intel bases, generators, and capture zones. Later, the evaluator can emit a richer goal descriptor without changing its decision policy.

This removes the need for:

- objective tapes
- verified proof graphs
- authored corridors
- CTF-specific return graph hacks
- map-specific direct-seek repairs
- per-objective direct-drive branches

Direct movement should remain only as a short-lived emergency recovery mechanism when a route transition fails—not as a second navigation system.

## Performance targets

These should become acceptance criteria after benchmarking:

- one graph build per `SimpleLevel`, shared by all bots
- no full `PlayerEntity.Advance` loop for normal graph construction
- no O(N²) portal pairing
- build target: under 100 ms for typical stock maps and under 250 ms for the largest stock maps
- steady-state path query: under 0.25 ms per bot, with zero allocations
- nearest surface/goal attachment through the spatial index, not full graph scans
- route recomputation only on invalidation or meaningful goal changes
- materially fewer nodes/links than current assets, with no fixed waypoint spacing

The graph should be built synchronously during level setup or match preflight. Background building can be added later, but it should not be required for correctness.

## 2026-07-27 composability checkpoint

The immediate bottleneck is now identified: individual contact edges can be
OG2-valid in isolation while the A* route assembled from them is not
state-composable. A live carrier can enter the next jump with residual
horizontal momentum from the preceding edge; the current edge contract does
not represent that incoming motion state. On Truefort the shared graph chose
the `158 -> 361 -> 436 -> 121` carrier route and repeatedly re-entered the
`361 -> 436` jump, while the Heavy-only graph chose a different validated
contact sequence. This is a graph/runtime contract failure, not justification
for weakening launch validation or restricting ascent edges to carriers.

The next implementation step is state-composable contacts: retain OG2
movement proof, record the source/launch state needed by each transition, and
make route selection reject or penalize incompatible predecessor-to-edge
transitions. A compact velocity/grounded state bucket or explicit setup
contact is preferable to ad-hoc speed slack. Full capture by every class on
all requested stock maps remains the acceptance gate before defaulting alpha.

## 2026-07-29 process postmortem

The eight-hour TwodFortTwo focus was a process failure, not evidence that the
map's geometry intrinsically requires ten minutes. The measured facts are:

- A narrow Pyro/Red/non-carrier TwodFortTwo build took about 106 seconds under
  v80. Its base contact phase took about 13 seconds; compound certification
  took about 92 seconds.
- The run that exceeded ten minutes used the full representative movement
  roster, both teams, and both carrying states. The generator replays expensive
  OG2 PlayerEntity control programs independently for those contexts. Map
  surface count is therefore not the dominant cost; context multiplication and
  repeated compound exploration are.
- Each context could perform a shallow exploration and then restart from the
  initial seeds for a deep retry. A graph artifact was written only after all
  contexts completed, so an interrupted build produced no reusable partial
  evidence.
- Generator fingerprint changes from v74 through v82 invalidated prior alpha
  graph-cache keys. We did not maintain a committed, known-good graph artifact
  set or a per-context resumable evidence cache before iterating, so changes
  could not be compared against the previously passing map set cheaply.
- The ten current-authority TwodFortTwo proof-tape replays are valid standalone
  route evidence, but they are not graph-gate or live-capture evidence. The
  filtered graph result remained 4/16, and the full roster graph was never
  validated.
- The first parallel expansion run reported mostly `load_failed` because the
  custom package search path was not set to the repository `Maps` directory;
  only built-in Eiger loaded. That run is invalid map coverage. The corrected
  runs were stopped before completion and are also not coverage evidence.

The operational mistakes were continuing to tune the hardest map after the
generator gate was known negative, treating route certificates as a proxy for
graph acceptance, failing to pin a known-good baseline before changing the
generator fingerprint, and launching the shipped-map matrix before the harness
was configured for custom packages. Consequently, we do not know that the
other maps remained passing after the v74-v82 changes; that assumption would be
unsafe.

The next work item is not another TwodFortTwo heuristic tweak. Freeze the
current experiment, implement context-scoped resumable compound evidence with
exact OG2 prediction state, correct the package-aware canonical map harness,
then run a small canary set against a preserved baseline before expanding to
all 42 graph representatives. No alpha-default or full-roster claim is
authorized until that canary and the complete capture matrix are green.

## 2026-07-30 live Valley execution correction

The `42/42` accelerated matrix above must not be read as proof that live
practice-bot execution was smooth. A live 8v8 Valley observation exposed a
separate executor-timebase defect: the probe certified OG2 contact schedules in
physics ticks, but the practice client only thought a small batch of bots per
update while continuing to apply their cached movement input between thoughts.
Bots could therefore run past the measured launch band before the next brain
update. Because the edge was marked certified, normal stuck escape was
suppressed and the bot waited for the certified-edge timeout. This produced the
visible Blue lower-stair/box stall and the Scout stair oscillation.

The correction is runtime-only and does not invalidate the graph topology:
active grounded certified contacts receive a navigation-only high-frequency
think until their jump pulse is issued; airborne contacts return to the normal
batched brain path. Completed alpha routes are also cooldown-protected from
per-update A* rebuilds. A traced Valley smoke run recorded zero failures on the
photographed lower-stair contacts `373->305`, `373->306`, and `373->307`.

`25.9` FPS observed minimum. This is a correction smoke result, not a renewed
